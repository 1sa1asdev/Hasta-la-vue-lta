# Teknisk skuld


| # | Vad | Var | Varför det är ett problem | Allvar |
|---|---|---|---|---|
| 1 | Rå SQL används i routes | `api/src/routes/guides.js`, `api/src/routes/tours.js`, `api/src/routes/photos.js` (bl.a. rad 24, 30, 37) | SQL byggs/utförs direkt i route-koden. Om användarindata kan nå dessa SQL-uttryck utan parametrisering finns risk för SQL-injektion. Databasåtkomst bör använda parametriserade queries eller en säker query-builder/ORM. | **Hög** |
| 2 | Databasanslutningen är hårdkodad | `api/src/routes/config.json` | Databasuppgifter/anslutningsinformation ligger i projektets konfiguration i stället för att hämtas från säkra miljövariabler eller motsvarande secret management. Om filen sprids eller checkas in kan credentials exponeras och bli svåra att rotera. | **Hög** |
| 3 | HTML från guides renderas direkt | Guides-relaterad rendering, bl.a. `schema.js` (rad 23) | HTML från data kan injiceras i sidan. Om innehållet inte är betrott/sanerat finns risk för XSS, där angriparen kan få JavaScript att köras i användarens webbläsare. | **Hög** |
| 4 | Alla API-routes är inte skyddade med `requireUser` | `api/src/auth.js` och berörda routes | Routes som borde kräva inloggning kan vara åtkomliga utan autentisering. Det kan leda till obehörig läsning eller ändring av data. Varje route behöver ett tydligt krav på om den är publik eller kräver användare. | **Hög** |
| 5 | API-servern hanterar inte ogiltiga ID:n robust | `api/src/index.js` | Ett ogiltigt ID har tidigare kunnat få servern att dö. Ett felaktigt request ska ge ett kontrollerat HTTP-fel och inte påverka resten av servern. Detta är ett tillgänglighets-/robusthetsproblem. | **Hög** |
| 6 | API-helpern kontrollerar inte HTTP-fel | `web/src/api.js`, `get()` | `fetch()` rejectar normalt inte promise vid t.ex. 404 eller 500. Om `res.ok` inte kontrolleras kan felaktiga svar behandlas som lyckade och orsaka svårbegripliga fel längre upp i UI:t. | **Medel** |
| 7 | API-anrop använder två olika mönster | `web/src/pages/Guides.jsx` rad 9, `GuideDetail.jsx` rad 9, `Profile.jsx` rad 9, `TourDetail.jsx` rad 9 använder rå `fetch`; `Home.jsx`, `Login.jsx` och `Tours.jsx` använder `api.js` | API-adress, felhantering och övrig kommunikationslogik blir spridd över flera komponenter. En förändring av API-konfigurationen måste då göras på flera ställen och det är lätt att missa ett. | **Medel** |
| 8 | API-fel hanteras inte konsekvent | `web/src/pages/Guides.jsx`, `GuideDetail.jsx`, `Profile.jsx`, `TourDetail.jsx` | Requests saknar konsekvent `catch`/error state. Vid nätverksfel eller API-fel får användaren ingen tydlig återkoppling. Detail-sidor kan dessutom fastna i `Laddar...` eftersom `null` används både för loading och ett läge där data aldrig kom fram. | **Medel** |
| 9 | `Home.jsx` saknar samlad loading/error-hantering för flera requests | `web/src/pages/Home.jsx`, bl.a. anropen till `/guides`, `/guides/popular`, `/guides/regions`, `/tours/latest` och `/health` | Flera requests körs samtidigt utan en tydlig gemensam strategi för loading och fel. Ett API-fel kan därför ge ett otydligt eller ofullständigt UI. Requests bör samordnas och sidan bör ha definierade loading- och error states. | **Medel** |
| 10 | Profilen hämtar alla tours och filtrerar i webbläsaren | `web/src/pages/Profile.jsx` rad 9–11, request till `/api/tours` | Klienten laddar ner alla tours trots att användaren bara behöver sina egna. Datamängden och belastningen växer med antalet tours. Backend bör filtrera, exempelvis via en användarspecifik endpoint/query. | **Medel** |
| 11 | `Home` hämtar data som även hämtas av underkomponenter | `web/src/pages/Home.jsx` rad 14–18 och motsvarande mindre subkomponenter | Samma eller mycket lik data hämtas flera gånger. Det ger onödig nätverkstrafik, väntetid och belastning och gör dataflödet svårare att förstå. Data bör ha en tydlig ägare/cache-strategi. | **Medel** |
| 12 | Auth-token och användare sparas i `localStorage` | `web/src/pages/Login.jsx` rad 18 | Långlivad känslig auth-information i `localStorage` kan läsas av JavaScript som körs på sidan. Vid en XSS-sårbarhet kan token därför stjälas. Auth-lagringen bör ses över tillsammans med XSS-skydd och serverns sessionsstrategi. | **Medel** |
| 13 | `Tours.jsx` använder `get()` men saknar felhantering | `web/src/pages/Tours.jsx` rad 10 | Central API-helper används, men utan `catch`/error state blir användarupplevelsen ändå otydlig när requesten misslyckas. | **Medel** |
| 14 | Logout använder full browser-navigation | `web/src/pages/Profile.jsx` rad 24, `window.location.href = '/'`; jämför `web/src/pages/Login.jsx` som använder `useNavigate()` | React Router används på andra ställen. Full omladdning är onödig och gör navigationen inkonsekvent. Logout bör använda samma routerstrategi som övriga interna navigeringar. | **Låg** |
| 15 | Olika implementationer av knappar | `web/src/components/Button.jsx`, `web/src/components/PrimaryButton.jsx`, `web/src/pages/Guides.jsx` och `web/src/components/Guide.jsx` | Det finns både återanvändbara knappkomponenter och direkta `<button>`-implementationer, med olika API/styling. Det ökar risken för inkonsekvent UI och gör gemensamma ändringar dyrare. | **Låg** |
